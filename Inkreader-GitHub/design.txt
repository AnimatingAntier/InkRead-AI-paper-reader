我把系统拆成"1个调度中枢 + 4个专职子agent"，正好对应你提的四个需求。上面这张图里，格式解析和长上下文管理属于"输入准备"层（论文进来后先做的事），网络检索和事实校验属于"回答生成与把关"层（真正回答问题时才触发）。下面逐个说设计细节。

编排调度 Agent（Orchestrator）

负责接收用户请求，判断这是"总结全文"、"针对性问答"、"提取关键信息"还是"多篇比较"，再决定要唤起哪些子agent、按什么顺序执行。它还要维护"多篇论文的上下文归属"——比如用户同时开着3篇论文，问"这三篇的方法有什么不同"，调度agent要知道去哪几个论文的知识库里分别取内容，而不是混在一起检索。

格式解析 Agent（对应"原生适配各种论文阅读"）

这个agent专门解决论文形式五花八门的问题，设计上建议做成"适配器模式"——针对不同输入类型注册不同的解析器，而不是写一套通用逻辑硬扛所有情况：

优先找LaTeX源码：如果论文来自arXiv，直接拉取.tex源文件解析，比对PDF做OCR或文本抽取准确得多，公式、表格结构都是原生的。
扫描版/图片版PDF：走OCR流程，同时保留原始图像用于关键图表的多模态理解。
双栏排版处理：需要按阅读顺序重新排列文本块，而不是简单按坐标从左到右扫，否则两栏内容会交错错位。
公式识别：转成LaTeX或MathML格式保留语义，而不是当成乱码文本。
参考文献结构化：把每条参考文献解析出题目、作者、年份，并尝试匹配DOI/arXiv ID，为后续"网络检索agent查这篇引文现状如何"做铺垫。

新增一种论文类型（比如某个领域特有的模板），只需要加一个新的解析适配器，不用改动其他agent，这也是"原生适配各种论文"在工程上的落地方式。

长上下文 Agent（对应"超长上下文"）

这部分基本承接我们之前讨论的方案：结构化切分章节→向量化建索引→总结类任务走Map-Reduce层级摘要→追踪论证脉络的场景走滚动摘要→多篇论文比较时先"抽取再比较"。这里再补充两个细节：

命名空间隔离：每篇论文的向量库要有独立的文档ID前缀，避免多篇论文一起检索时把不同论文的内容混进同一个答案。
检索覆盖度自评估：检索到的内容如果和问题的相关度都很低（比如向量相似度分数普遍偏低），这本身是个信号——说明论文里可能真的没有答案，这个信号要传给调度agent，触发"要不要转去问网络检索agent"的判断。
网络检索 Agent（对应"可搜索网上资料并应用于回答"）

这是这次新增的能力，设计上有几个关键点：

什么时候该触发联网搜索，而不是滥用：

论文内部检索覆盖度低（上面提到的信号）
问题本身带有明显的"当下"意图，比如"这篇论文的方法现在有没有被超越"、"这个数据集现在的SOTA是多少"、"作者后来还发表了什么相关工作"
用户显式要求，比如"帮我查一下这篇论文的后续引用情况"

信息源的选择：优先用学术类信息源（arXiv、Semantic Scholar、DBLP、期刊官方页面），而不是无差别的通用网页搜索，减少噪声和不可靠信息混进答案。

最关键的设计点——来源隔离：网络检索到的内容和论文原文内容必须在prompt里明确分区、并在最终答案里分别标注"论文原文"vs"网络检索（附来源链接）"。这一点很容易被忽略，但如果混在一起喂给模型，很可能出现"张冠李戴"式的新型幻觉——比如把网上搜到的后续工作的结论，误说成是这篇论文本身的结论。

事实校验 Agent（对应"资料依据可信真实"）

这是整个系统的"守门员"，不管答案是来自论文内部检索还是网络检索，都要过一遍：

溯源标注：每条结论标注来源（论文的具体章节/页码，或网络来源的链接）
蕴含关系校验：用轻量NLI模型检查"生成的这句话"是否真能从对应的原文片段推出来，推不出来就打回重写
一致性采样：对关键结论换个问法多问几次，看输出是否稳定，不稳定就标"低置信度"
显式拒答：论文和网络都没找到答案时，明确说"未找到相关信息"，不能因为"总要说点什么"就编
一个简单的例子串一下

假设用户问："这篇论文提出的方法，现在还是SOTA吗？"

调度agent识别出这需要"论文内部方法描述"+"当前最新进展"两部分 → 长上下下文agent从论文里取出方法的原始描述 → 网络检索agent去查这个任务/数据集上最近的排行榜和后续论文 → 两部分内容分别标好来源交给事实校验agent → 校验agent确认"论文方法描述"确实来自原文、"当前SOTA信息"确实来自检索到的网页，没有互相污染 → 最终答案里两部分会分开呈现，各自带来源链接。


补充的三个模块

除了你列的5个，工程落地还必须有这三块，否则系统跑不起来或者跑起来了但不可控：

存储与基础设施层：5个Agent都要读写数据，没有统一的存储层，各Agent就会各自为政、数据不一致
评测与可观测性：没有量化指标，就没法判断"事实校验Agent到底有没有在起作用"，也没法在出问题时定位是哪个环节
安全与成本治理：涉及用户私有论文和外部API调用成本，这两项一旦忽视，轻则超预算、重则数据泄露
技术选型总览
模块	推荐技术选型	关键理由
编排调度	LangGraph（状态机式编排）或轻量自研state machine	需要显式的条件分支（要不要联网、要不要多篇比较），LangGraph的图结构比对话式框架（AutoGen/CrewAI）更好debug
格式解析	GROBID（学术论文结构化解析）+ PyMuPDF（坐标/表格提取）+ 优先拉取arXiv LaTeX源码	GROBID专门针对学术论文训练，章节/参考文献识别准确率高于通用PDF解析库
长上下文	向量库：Qdrant/Milvus（自建）或托管服务；Embedding：支持中英双语、8K+长度的模型	开源向量库便于私有化部署，满足论文隐私要求
网络检索	Semantic Scholar API / arXiv API / CrossRef 优先，通用搜索API兜底	学术API返回结构化的引用数、后续工作信息，比通用搜索噪声小得多
事实校验	轻量NLI模型（entailment判断）+ LLM二次复核	纯LLM复核成本高，NLI模型做第一道快速过滤，可疑的再交给LLM精细判断
存储与基础设施	对象存储(S3/MinIO)存原始PDF；PostgreSQL存元数据/会话；Redis做缓存；消息队列(Celery/RQ)处理耗时任务	解析和向量化都是耗时操作，必须异步化，否则用户上传论文时界面会卡住
评测与可观测性	自建评测集（可参考QASPER等论文问答数据集）+ 全链路日志追踪(OpenTelemetry)	需要能追踪一次问答请求经过了哪些Agent、每步耗时和成本，出问题能定位到具体环节
安全与成本治理	多租户隔离（每用户独立命名空间）+ API用量监控告警	私有论文不能跨用户串库；长论文批量处理容易导致API成本失控，需要预算护栏
关键接口设计

Agent之间需要统一的数据契约，否则每加一个Agent都要重新对接。核心是两份schema：

论文结构化数据（格式解析Agent的输出，其他Agent的输入）

json
{
  "paper_id": "string",
  "title": "string",
  "sections": [
    {"name": "abstract", "text": "...", "order": 0}
  ],
  "figures": [{"caption": "...", "page": 3, "image_ref": "..."}],
  "tables": [{"caption": "...", "page": 5, "data_ref": "..."}],
  "equations": [{"latex": "...", "context": "..."}],
  "references": [{"title": "...", "year": 2023, "doi": "...", "arxiv_id": "..."}]
}

检索结果（长上下文Agent / 网络检索Agent 共用的返回格式，方便事实校验Agent统一处理）

json
{
  "source_type": "paper_internal | web_search",
  "content": "string",
  "citation": {"section": "3.2 实验设置", "page": 5, "url": null},
  "relevance_score": 0.87
}

统一source_type字段是这里最关键的设计——事实校验Agent靠这个字段决定该用"论文原文"还是"网络检索"的标注方式呈现给用户，这也是防止两类信息源被模型混淆的工程手段。

分阶段路线图
阶段	周期	目标	交付物
Phase 1（MVP）	4-6周	验证单篇论文的核心可行性	格式解析 + 长上下文Agent，支持单篇论文总结与问答，暂不含网络检索
Phase 2	约4周	补齐可信度与多篇能力	加入事实校验Agent与溯源标注；支持多篇论文比较；扩展格式解析对更多论文模板/领域的适配
Phase 3	约4周+	补齐联网能力与工程化	加入网络检索Agent；完成编排调度的完整多Agent协同；上线评测与监控体系

建议按这个顺序推进而不是一开始就做全量：事实校验和长上下文是"地基"，联网检索反而是最后才加的能力，因为它涉及的来源隔离设计如果在系统跑通之前就引入，会让早期调试变得复杂。

评估指标体系
模块	核心指标
格式解析	章节识别准确率、公式/表格提取成功率
长上下文	检索命中率（recall@k）、摘要对原文的信息覆盖度
网络检索	触发时机准确率（该联网时联网、不该联网时不误触发）、来源可靠性占比
事实校验	幻觉拦截率（人工抽检结合NLI校验结果）、误拒率（把正确内容错误标记为不支持）
整体系统	端到端响应延迟、单次问答API成本、用户对答案的采纳/纠正率
主要风险与应对
检索质量差导致下游全崩：给长上下文Agent的检索结果加置信度阈值，低于阈值触发降级（提示"未找到足够依据"而非硬答）
网络检索引入的噪声污染答案：来源隔离设计（上面提到的source_type字段）+ 学术API优先，通用搜索仅作兜底
多Agent链路延迟叠加：耗时的解析和向量化环节异步化，问答类请求走同步快路径，避免用户等待过久
成本失控：对长论文的分块摘要、批量比较等高消耗场景设置Token预算上限，超限时自动降级为"先给出可用部分+提示剩余部分需要更多时间"
